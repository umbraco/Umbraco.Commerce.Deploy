# Upgrade to Umbraco 19

From Umbraco Commerce `[18.1.0, 18.999.999)` + Umbraco Deploy `[18.0.0, 18.999.999)` (CMS 18) to Umbraco Commerce `19.0.0-beta.1` + Umbraco Deploy `19.0.0-beta1` (CMS `19.0.0-beta1`, tag `release-19.0.0-beta1`).
Branch `v19/topic/cms-19-upgrade` → PR into `release/19.0.0`, both cut from `main` (`a53c4ce`).

**Targets CMS release:** `release-19.0.0-beta1`, via Umbraco Commerce `19.0.0-beta.1` and Umbraco Deploy `19.0.0-beta1` (Deploy tag `release-19.0.0-beta1`, MyGet `umbracoprereleases`). The package's own version is `19.0.0-beta.1`.

The package has no direct `Umbraco.Cms.*` references; CMS changes reach it through Commerce (Core repo, `docs/upgrades/v19.md`) and Deploy (umbraco/Umbraco-Deploy PRs #1162 and #1163).

## Decisions

- Tasks 1 to 3 landed as one commit (`fd89abb`): the bump doesn't compile without the two code fixes, and each commit must build.
- Registration moved to the composer as `Configure<DeployEntityTypesOptions>`, the only way Deploy 19 offers.
- Client entity actions follow the server flags, the same way Deploy registers them for CMS entities: Queue and Export on items and collections, Tree Restore on the product attribute and preset collections, Partial Restore on the product attribute and preset items. Partial Restore isn't on the collections, because Deploy preselects the node's unique, and a collection's unique is the store ID.
- The collections (and the "Options", "Taxes" and "Templates" groups that reuse their entity types) use the store ID as unique, which the connectors treat as the root, so queueing, exporting or restoring a store's collection covers that entity type in every store. Same as v18.
- The remote tree lists the product attributes and presets of all stores flat at the root, with the store name added when there's more than one store.
- The UDA refresher is one handler class implementing `IAsyncEventHandlerFor<T>` for the 26 saved and deleted notifications of the 13 settings entity types, because Commerce's notifications share no base with the entity. Commerce's async `EventHub.NotificationEvents.On…Saved(Func<…, Task>)` overloads aren't an option: for 13 entities, including 9 of the settings types, they are typed to the `…CreatingNotification`. Deletes remove the UDA file by UDI, without getting the artifact of the deleted entity. Signatures aren't refreshed, because Deploy only caches the signatures of CMS entity types (`CurrentEnvironment.CacheSignature`).

## Breaking changes for consumers

- Requires Umbraco 19, Umbraco Commerce 19 and Umbraco Deploy 19 (.NET 11). Deploy 19 won't transfer to or from a Deploy 18 environment.
- `UmbracoCommerceDeployComponent` constructor no longer takes `ITransferEntityService`; entity types are registered on `DeployEntityTypesOptions` in `UmbracoCommerceDeployComposer`.
- `UmbracoCommerceVariantsEditorValueConnector.VariantsBlockEditorLayoutItem` now derives from `BlockLayoutItemBase`; obsolete `ContentUdi`/`SettingsUdi` removed.

## Follow-ups

- `ShippingMethodArtifact` has an `[Obsolete("Now handled via CalculationConfig")]` member with no removal version: decide whether to remove it.
- Commerce Core: for 13 entities (9 of them settings types), the async `EventHub.NotificationEvents.On…` overloads register for the `…CreatingNotification` (copy-paste), e.g. `OnCurrencySaved(Func<CurrencyCreatingNotification, Task>)`. Reported as internal Umbraco Commerce work item 73806 (16-11-2026).
- Raise the Commerce and Deploy floors to `19.0.0` at the stable release, and recheck the `NuGet.config` mapping then: `Umbraco.Commerce.*` restores from MyGet only, and stable Commerce ships to nuget.org (applies to every add-on).
- Pre-existing, by design: on SQLite, Commerce Deploy points Commerce at its own `Umbraco.Commerce.sqlite.db`, so a site that already keeps Commerce data in `Umbraco.sqlite.db` (the DemoStore) boots with an empty store and its product pages 500. Worth a docs note or a check before switching.
- DemoStore `release/19.0.0` still has a data type on the removed `Umbraco.MediaPicker` editor; a Deploy schema import of the whole site fails on it. DemoStore issue, not this package.
- `ProductAttributeArtifact` hides `IArtifact.Name` with a `TranslatedValueArtifact<string>`, so Deploy sees no name for product attributes (logs, mismatch reports). The remote tree no longer depends on it.
- Scope collection actions to their store: a store-scoped range would need a pseudo UDI, so it's left as all stores for now.
- Commerce Core: variant layout items saved on v19 carry `key: 00000000-...` (from `BlockLayoutItemBase`), same as what Deploy now writes. Check with Core whether variants need a real layout key for reusable elements.

## Backport candidates

- Empty-string price handling in `UmbracoCommercePriceValueConnector`: a price saved as `{"<currency>": ""}` (no price for that currency) failed to parse, logged an error per item (135 on a DemoStore export) and dropped the whole price. Fixed in `eb0abea`: empty strings read as no price, numeric strings are parsed, anything else is a warning for that currency only. Same code on v18 and v17: backported as `v18/topic/empty-price-value` → `hotfix/18.1.1` and `v17/topic/empty-price-value` → `hotfix/17.1.1` (11-11-2026; v18 re-tested on a v18 DemoStore, v17 build only).
- Connector ranges, client entity actions, BackOfficeOnly support and the UDA refresher handler: backported without breaking changes as `v17/topic/deploy-entity-actions` → `hotfix/17.1.1` (#33) and `v18/topic/deploy-entity-actions` → `hotfix/18.1.1` (#34) (16-11-2026). Deploy 17 and 18 neither register UDI types nor make disk entity types transferable in the BackOfficeOnly edition, so the backports keep the UDI registration and add an internal component that registers the settings types as transfer entity types when the configured edition is BackOfficeOnly. The remote tree (`ITreeServiceConnector`) isn't backported, because it needs Deploy 17.4 or 18.2. v18 smoke-tested on a v18 DemoStore in the BackOfficeOnly edition; v17 build only.
